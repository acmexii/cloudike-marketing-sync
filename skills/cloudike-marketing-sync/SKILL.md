# 클라우다이크 마케팅 자료 최신화

## 기본 대상과 재사용
- 문서 산출물은 서비스 소개서 PPTX 1개와 그 최종본에서 출력한 PDF 1개, 총 2개다. 홈페이지용·앱 기능소개용 문서를 별도로 생성하지 않는다. 홈페이지의 `소개자료` 메뉴·카드는 이 PDF를 직접 가리켜야 한다. 홈페이지 배포본과 승인된 Drive 사본은 같은 두 파일의 복사본이며 별도 문서로 세지 않는다. 과거 상태에 앱 기능소개서 등 여러 관리 문서가 있어도 자동으로 제작 범위를 확대하지 않는다. 추가 문서는 사용자가 별도로 요청한 경우에만 포함한다.
- 소개서 콘텐츠의 기준은 앱 서비스 https://acmexii.github.io/cloudikehome/app/ 의 전체 기능이다. 기존 전체 기능을 빠짐없이 소개하고 신규 기능은 적절한 위치에 추가하며 변경 기능은 기존 설명·화면을 갱신한다. 변경 기능만 모은 요약본으로 전체 기능 소개서를 대체하지 않는다.
- 홈페이지 https://acmexii.github.io/cloudikehome/ 는 완성된 PDF의 소개자료 링크 게시·다운로드 검증 용도로만 사용한다. 홈페이지의 홍보 문구, 랜딩 화면·캡처, 요금표, 고객사·사례, 문의·상담·프로모션 등 홈페이지 콘텐츠는 소개서 본문에 포함하지 않는다. 앱에서 직접 확인되는 기능·화면만 근거로 사용한다. 공식 로고의 홈페이지 출처 기록은 브랜드 자산의 출처이며 홈페이지 내용을 본문에 포함하는 허용 근거가 아니다.
- 앱 기본 URL: https://acmexii.github.io/cloudikehome/app/ . 영상은 승인된 Git 변경이 배포된 실제 앱을 직접 조작하며 녹화한다. 변경된 앱의 배포 URL이 따로 지정되면 해당 URL을 사용한다. 홈페이지의 소개자료 링크에는 서비스 소개서의 동일한 최종 PDF를 직접 연결하고, 최종 영상은 프로젝트 로컬에만 보관하며 Drive에 업로드하지 않는다.
- 공식 브랜드 로고: [assets/cloudike-logo.png](assets/cloudike-logo.png). `https://cloudike.kr/`의 헤더에서 추출한 원본이며, 출처·확인일·크기·해시는 [출처 기록](assets/cloudike-logo-source.json)에 보관한다. 소개서 표지·본문 브랜드 영역 및 영상의 필요한 브랜드 표시에 이 자산을 재사용한다. 원본 비율·색·투명도를 유지하고 작은 원본을 과도하게 확대하지 않는다. 텍스트로 로고를 재현하거나 템플릿의 MSASchool·유엔진 로고를 Cloudike 로고 대신 쓰지 않는다. 공식 로고 변경이 확인되면 새 자산과 교체 범위를 사전 승인안에 포함한다.
- 저장소: https://github.com/acmexii/cloudikehome , 기준 브랜치 `main`. PR URL은 선택 입력이며, 저장소에서 대상 커밋에 연결된 PR을 자동 조회한다.
- 작업공간의 `outputs/cloudike-marketing-sync/`에 실행 상태와 결과물을 관리한다. 최초에 기존 소개서를 검색하고 관리 대상을 연결한다. 로컬 전용 모드에서는 기존 문서를 로컬·공개 저장소에서 찾고 Drive 연결·폴더 선택을 요구하지 않는다. 게시 가능 모드에서 Drive 폴더가 미지정이면 연결된 도구로 후보를 확인하고 모호한 경우 선택받는다.
- 문서 생성·수정 시마다 최신 `artifact-template-msaschool-purple` 스킬을 반드시 적용한다. `skill-slide-msaschool`은 배포 저장소 이름이며 실제 스킬 이름은 `artifact-template-msaschool-purple`이다. 제작 전 설치본과 배포 저장소 `https://github.com/acmexii/skill-slide-msaschool`의 현재 버전을 비교하고, 최신 `SKILL.md`, 디자인 규격·레이아웃 지도와 해당 문서 유형의 참조 이미지를 읽는다. 과거 실행의 지침·생성 스크립트·기억만으로 제작하지 않는다. 설치본이 오래됐으면 최신 지침·자산을 확인해 사용하되 로컬 수정은 자동 덮어쓰기하지 않는다. 스킬 누락·접근 실패로 최신 규격을 확인할 수 없으면 해당 문서 제작을 보류하고 원인을 알린다. 임의의 보라색 템플릿으로 대체하지 않는다. PPTX/PDF 실제 제작에는 Presentations 및 PDF 스킬의 검수 절차를 적용한다.
- 영상 제작에는 형제 스킬 [cloudike-service-video](../cloudike-service-video/SKILL.md), [마우스 연출](../cloudike-service-video/references/interaction-motion.md), [ElevenLabs 설정](../cloudike-service-video/references/elevenlabs.md)을 읽고 재사용한다. 이 스킬에서는 대상 URL과 길이 20~40초를 우선한다. API·녹화 도구 지원은 실행 환경에서 확인한다.

## 실행 모드
시작 시 [인증·쓰기 권한과 실행 모드](references/source-and-state.md#인증쓰기-권한과-실행-모드)에 따라 대상 저장소의 권한을 읽기 전용으로 확인한다. GitHub 인증 및 쓰기 권한이 확인되면 `publish_capable`, 없거나 확인 불가하면 `local_only`로 진행한다. 역할 이름이나 저장소 소유자 이름으로 권한을 추정하지 않는다.

`local_only`에서도 Git 변경 감지·제작 사전 승인·최신 템플릿·실제 화면·영상 검수 절차는 동일하다. PPTX·PDF·영상과 제작 기록을 로컬에만 생성한다. 로그인·토큰 입력·포크·권한 부여를 요구하지 않으며 Git 커밋·푸시·PR 제출, Drive 업로드, 홈페이지 게시를 수행하지 않는다. 문서 2개 완성·검수 후 담당자에게 보여 주고 명시적 확인을 받아 영상 제작을 이어간다. 영상까지 완료 후 로컬 결과물 링크와 검수 결과를 안내하고 “문서 생성 완료. GitHub 반영은 강사가 진행합니다.”라고 알린 뒤 종료한다. PR 제출 여부도 묻지 않는다. 제작에 필요한 별도 도구·음성 서비스의 장애는 실제 미완료 사항으로 보고한다.

## 필수 실행 순서
1. **Git 게이트:** 최초에는 현재 main 커밋을 최초 처리 대상으로 삼는다. 이후에는 마지막 완료 커밋 이후 앱 서비스 전체 기능에 영향을 주는 변경과 연결된 PR의 Diff를 확인한다. 미병합 PR은 분석만 하고 제작·게시 대상으로 확정하지 않는다. 새 관련 커밋 또는 실제 앱 서비스 기능·화면 변경이 없으면 사용자에게 정확히 `변경 된 사항이 없습니다.`라고 알리고 즉시 종료한다. 승인안 작성·캡처·녹화·문서 생성/수정·TTS·Drive 업로드·홈페이지 게시를 진행하지 않는다. 미완료 실행이 있어도 일반 실행에서는 자동 재개하지 않는다. 사용자가 미완료 작업 재개를 명시적으로 요청한 경우에만 기존 승인 범위에서 재개한다. 상세 판단과 상태는 [Git과 실행 상태](references/source-and-state.md)를 따른다.
2. **변경안 준비:** 승인 전에는 Git·기존 소개서·Drive 파일을 읽고, 앱을 열어 기능 배포를 확인하고, 홈페이지는 PDF 연결 위치를 확인하는 데만 사용한다. 결과물 생성·기존 문서 수정·Drive 쓰기·영상 녹화·유료 합성·게시를 시작하지 않는다. [사전 승인안](references/approval-and-documents.md)의 표를 작성한다.
3. **마케팅 팀 명시적 승인:** 대상 문서 목록, 페이지/슬라이드·섹션, 변경/추가 구분, 기존 내용과 반영 내용, 영상 및 게시 범위를 제시하고 기다린다. 무응답·경과 시간·스킬 호출 자체는 승인이 아니다. 최초 생성도 페이지별 구성 승인이 필요하다. 일부 승인 시 승인된 범위만 진행한다. 승인 후 대상 커밋이나 내용이 달라지면 다시 승인받는다.
4. **실제 화면 확보와 제작:** 승인된 커밋의 기능이 대상 앱에 실제 배포됐는지 검증한다. 이전 값이면 배포 대기로 기록하고 쓰기를 중단한다. 먼저 문서용 화면을 직접 탐색·캡처하여 서비스 소개서 PPTX 1개와 파생 PDF 1개를 제작한다. 이 단계에서는 영상 녹화·영상 편집·유료 음성 합성을 시작하지 않는다. 영상 제작은 다음 단계의 담당자 확인 후에만 진행한다. 정적 사본에 변경 기능이나 실제 반응이 없으면 해당 영상 제작을 보류하고 동작하는 배포 앱이 필요함을 알린다. [문서 처리](references/approval-and-documents.md), [영상 처리](references/video-production.md)를 수행한다.
5. **반영과 검수:** PPTX를 렌더링해 검수하고 같은 최종본에서 PDF를 출력한다. PPTX·PDF 2개가 완성되면 두 파일의 링크, 페이지 수, 주요 변경과 검수 결과를 담당자에게 보여 주고 확인을 받는다. 담당자는 이 대화의 사용자가 맡을 수 있으며 별도 메시지를 보내지 않는다. 확인 전에는 영상 녹화·편집·유료 합성을 시작하지 않는다. 최초 제작 승인이나 PR 제출 승인은 이 완성 문서 확인을 대신하지 않는다. 수정 요청이 있으면 문서를 수정·검수하고 다시 보여 준다. 담당자의 명시적 확인 후 승인된 영상 장면·대본 범위에서 실제 앱 조작 녹화와 지정 음성 합성을 이어서 수행하고 검수한 MP4를 프로젝트 `outputs/cloudike-marketing-sync/videos/<change_id>/`에 저장한다. 영상 범위가 변경되지 않았다면 동일한 영상 제작 승인을 중복 요청하지 않는다. `local_only`도 이 문서 확인→영상 제작 순서를 동일하게 적용하며 영상 완료 후 로컬 결과를 안내하고 종료한다. 아래 외부 반영 절차는 `publish_capable`에만 적용한다. Drive에는 PPTX·PDF만 생성하거나 기존 ID에 새 버전으로 반영한다. 최종 MP4와 제작 원본은 프로젝트 로컬에만 보관하고 영상은 Drive에 업로드하거나 홈페이지에 게시하지 않는다. 홈페이지의 소개자료 링크에는 서비스 소개서의 동일한 최종 PDF를 직접 연결하며 [다운로드 링크와 배포 검증](references/approval-and-documents.md#홈페이지-다운로드-링크와-배포-검증)에 따라 전체 페이지의 복제 메뉴와 실제 다운로드를 검증한다. PR 방식에서는 문서 생성·검수가 끝난 후 완성된 파일과 변경 요약을 먼저 안내하고, 별도의 PR 제출 승인을 받은 뒤 저장소에 반영한다. 제작 전 마케팅 팀 승인만으로 PR을 제출하지 않는다. 상세 절차는 [문서 완료 안내와 PR 제출 승인](references/approval-and-documents.md#문서-완료-안내와-pr-제출-승인)을 따른다. 승인된 게시 방식에 맞춰 배포 결과를 확인한다. 커밋·푸시·PR 생성·병합·배포 완료를 구분하며 GitHub Pages를 로컬 파일 복사만으로 배포 완료라고 보고하지 않는다.
6. **결과 보고와 상태 기록:** 결과물 링크, 반영 커밋, 변경 위치, 검수 결과, 미완료 작업을 보고한다. 결과물별 성공을 기록하고 필수 단계가 모두 성공한 경우에만 완료 기준을 이동한다. 실패하면 성공한 단계를 중복 실행하지 않고 승인 범위 안에서 재개한다.

## 콘텐츠 원칙
소개서는 앱 서비스 전체 기능을 다룬다. 앱 화면·메뉴·기능 목록을 조사해 기능별 소개서 페이지·화면·설명을 대응시킨 전체 기능 커버리지 표를 유지한다. 신규 기능은 관련 흐름에 추가하고 변경 기능은 기존 문구·표·캡처와 반복 언급을 갱신한다. 삭제·폐지 기능은 종료 여부를 근거로 반영한다. PR의 추가·변경 기능뿐 아니라 변경되지 않은 기존 기능도 소개서에 유지하며, 과거 소개서가 홈페이지 중심이면 이를 그대로 보존하지 말고 앱 전체 기능 중심으로 교체하는 계획을 제시한다. 홈페이지 홍보·가격·문의 내용을 앱 기능으로 오인해 포함하지 않는다. PR에서 확인한 각 앱 변경을 서비스 소개서 PPTX와 동일 내용의 PDF에 연결하고, 앱에서 실제로 확인하지 못한 동작이나 효익은 만들어내지 않는다. 앱의 실습 범위와 실제 서버 동작의 차이를 정확히 설명한다.

## 스킬 생성과 실사용 구분
스킬 작성·검증 요청만으로 홈페이지 수정, 커밋·푸시, Drive 업로드, 유료 TTS 또는 영상 제작을 실행하지 않는다. 실제 최신화 시에는 위 사전 승인 단계가 반드시 적용된다. 키·토큰·DPAPI 파일은 결과물·상태 파일·저장소에 넣지 않는다.
